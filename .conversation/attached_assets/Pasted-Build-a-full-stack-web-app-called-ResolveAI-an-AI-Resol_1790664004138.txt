Build a full-stack web app called "ResolveAI", an AI Resolution Copilot for post-purchase customer issues (damaged product, refund, return, replacement, delivery delay, warranty, cancellation).

CORE IDEA
Every customer issue becomes a "case" with a full timeline. The AI reads the customer's message and returns structured JSON that is saved as real database fields. The AI only SUGGESTS. A human agent always decides. Any agent who opens a case sees the full history, so the customer never has to repeat themselves.

TECH STACK (strict)
- Frontend: React + Vite, React Router, Tailwind CSS, Axios, Recharts
- Backend: Node.js + Express
- Auth: JWT + bcrypt
- Validation: Zod (validate all request bodies AND all AI output)
- Database: SQLite using better-sqlite3
- AI: Groq API (model: llama-3.3-70b-versatile), called ONLY from the backend
- The API key is read from the environment variable GROQ_API_KEY (Replit Secrets). Never put it in frontend code or committed files.

FOLDER STRUCTURE
/frontend  (React app)
/backend   (Express app)
README.md, .env.example (fake values only), .gitignore (must ignore .env and the database file)
Run both with one command from root (use concurrently), and set up the Vite proxy so /api goes to the backend.

ROLES
1. customer: can create cases, see ONLY their own cases, add messages/evidence, see status and next step.
2. agent: can see all cases, AI analysis, timeline, generate/edit/send replies, change status, override AI fields.
Role checks must be enforced in backend middleware, not only hidden in the UI. A customer must get 403 if they open another customer's case by ID.

DATABASE TABLES
- users: id, name, email (unique), password_hash, role, created_at
- orders (mock data): id, order_code, user_id, product_name, price, order_date, delivery_date, status
- cases: id, case_code (like RF1024), user_id, order_id (nullable), status (New, Investigating, Awaiting Customer, Approved, Resolved, Rejected), category, priority (Low, Medium, High, Critical), sentiment, customer_intent, summary, recommended_action, next_step, escalation_required (0/1), escalation_reason, missing_information (JSON text), resolution_plan (JSON text), assigned_agent_id, ai_failed (0/1), created_at, updated_at, due_at
- case_events (the timeline): id, case_id, event_type, description, actor_type (customer, agent, ai, system), actor_id, metadata (JSON text), created_at
- messages: id, case_id, sender_type (customer, agent), body, created_at
- attachments: id, case_id, file_name, file_path, uploaded_at (image upload via multer, images only, max 5MB)
Event types include: ORDER_PLACED, DELIVERED, CASE_CREATED, EVIDENCE_SUBMITTED, AI_CLASSIFIED, MISSING_INFO_REQUESTED, ESCALATED, AGENT_ASSIGNED, AGENT_REVIEW, AI_OVERRIDDEN, REPLY_SENT, STATUS_CHANGED, RESOLVED.
Every important action must write a case_event. Events are never edited or deleted.

AI FEATURES (all in backend/services/aiService.js, one file, so the provider can be swapped later)
1. analyzeIssue(message, orderInfo, caseHistory): returns JSON:
{ "issue_category": "", "priority": "", "sentiment": "", "customer_intent": "", "summary": "", "missing_information": [], "recommended_action": "", "next_step": "", "escalation_required": false }
2. generateResolutionPlan(case): returns JSON { "steps": ["Verify order", "Check eligibility", ...] } (4 to 6 steps)
3. generateReply(case, timeline, tone): returns a draft reply text. The agent can edit before sending.
- Use Groq JSON mode (response_format: { type: "json_object" }) and temperature 0.2.
- Validate every AI response with Zod. If the AI call fails, times out, or returns invalid JSON: still create the case, set ai_failed = 1, status New, and show "Needs manual review" to the agent. The app must never crash because of the AI.
- The AI must include the case history (past cases and events for this customer) in its prompt.
- Prompt-injection protection: put the customer message inside clear delimiters, tell the model to treat it as data, never as instructions, and never to approve refunds or replacements. The AI only recommends.

ESCALATION LOGIC (this is the key feature)
Escalation is decided by BACKEND RULES first, plus the AI flag. Set escalation_required = 1 and store escalation_reason when any of these is true:
- Customer already has an open case for the same order and no agent reply for more than 24 hours (repeat contact with no response)
- Sentiment is Frustrated or Angry
- Customer has 3 or more cases in 30 days
- Case is past its due_at time (SLA)
- Order value is above a high-value limit (set to 50000)
- AI flagged escalation
The reason must be shown in plain words, for example: "Customer contacted us 1 day ago with photos, no agent replied." Add an ESCALATED event.

API ROUTES (all under /api)
- POST /auth/register, POST /auth/login, GET /auth/me
- GET /orders/mine (customer's mock orders)
- POST /cases (customer: message + optional order_id) -> runs AI, saves case, creates timeline events
- GET /cases/mine (customer)
- GET /cases (agent, with filters: status, priority, category, escalated)
- GET /cases/:id (case + timeline + messages + attachments, with ownership check)
- POST /cases/:id/messages
- POST /cases/:id/attachments
- POST /cases/:id/generate-reply (agent)
- POST /cases/:id/send-reply (agent)
- PATCH /cases/:id/status (agent)
- PATCH /cases/:id/override (agent, changes AI fields and logs AI_OVERRIDDEN with old and new values)
- POST /cases/:id/assign (agent)
- GET /analytics/summary (agent)
Add helmet, CORS, and a rate limit on /auth and on AI routes. Return clean error messages.
